# Python AI 服务与数据加工架构指南

目标：从业务输入和交付约束出发，选择足够简单、能够运行和维护的方案。此文是决策与实现约束，不是强制安装全部组件的模板。用户明确要求、目标仓库的 AGENTS.md 和既有平台契约优先。先阅读仓库文档、依赖、入口、部署方式和实际接口；默认沿用已有成熟栈，除非需求明确要求迁移。

## 一、先判断场景，再选技术

动手前收集或从代码推断：调用方与协议、数据来源/权限、输出及验收、数据规模与格式、实时或离线、并发与耗时、机器/GPU及现成基础设施、平台调度边界、失败重试/恢复要求。未知项标记为假设；只有阻塞正确实现的事项才提问。给出简短选择说明：场景、选型、理由、替代方案或不采用的原因、主要假设与瓶颈；再实现而不是停留在建议。

### 先按四个相互独立的维度描述需求

1. **业务时效**：离线批处理，或在线/近实时加工。离线通常面向已确定的有界数据集，优先关注完成期限、吞吐、成本与可重跑；在线通常随请求或事件持续到达处理，更关注端到端时效、可用性及积压。时间阈值由业务 SLA 决定，不擅自用秒数划线。离线可以高频增量；在线可采用批处理技术。
2. **数据形态**：有界批次、无界事件流，或分窗口/微批增量；流/批描述数据和计算方式，与在线/离线不是严格一一对应。区分在线逐条请求、持续流式事件处理；需要时分别考虑吞吐、状态和窗口。
3. **部署和交付**：单机/多机、CPU/GPU、独立作业或对外提供算子服务；平台算子服务是接入/交付方式，不与在线或离线并列为互斥类型。
4. **交互方式**：同步请求等待结果、异步提交后查询/回调，或订阅事件/消息。异步不等于离线，同步 HTTP 入口不证明实时；流式模型输出也不等同于流式数据加工。

按上述四维与现有平台决定选型，不因“在线/离线”“大规模”或“平台算子”之一自动强制引入特定框架。典型组合：离线 + 平台 POST 提交数据集 ID + 后台批量加工；在线 + 平台 POST 单条数据 + 同步响应；近实时 + 消息流消费/微批 + 持续输出；在线接入 + 异步排队也可能满足时效要求。先确认平台 POST 传的是作业配置、数据引用还是每条实际数据，不假设其语义。

### 选型表

| 场景与触发条件 | 默认方案 | 选择或升级条件 |
| --- | --- | --- |
| 企业知识、数据库问答；模型/工具编排；请求需要即时返回 | 新建 API 首选 FastAPI + Pydantic，模型 SDK 或 HTTPX；保留已有 Flask | 流式时确认上下游均支持；异步 I/O 使用异步客户端。只在需要时引入检索、工具、数据库等依赖；不能杜撰企业知识库和数据表。 |
| 单机短小数据脚本 | 普通 Python + 清晰 CLI / 函数，按需批处理与并发 | 不为后台队列引入基础设施；若要后台任务、队列缓冲、失败重试，再评估 Celery。 |
| 独立分片、长任务、后台排队或进度查询 | 现有 Celery + RabbitMQ；无现成组件且需求成立时作为候选 | 单机或多机均可；Worker 按数据分片运行。小规模一次性处理不强制队列。Broker 和结果存储是不同职责，先确认已有服务。 |
| 跨节点 Python/多模态预处理、离线模型推理、CPU/GPU 调度 | Ray / Ray Data | 集群与数据路径可用，且模型常驻、数据供给或扩容确有需要；单机 Ray 不能证明多机。 |
| 大规模结构化数据、SQL、关联、聚合、全局去重 | Spark / PySpark | 数据、集群或平台已有 Spark，且规模或操作复杂度足以抵消开销；关注分区、Shuffle、数据倾斜、存储。 |
| 在线逐条/小批数据处理，调用方等待结果 | 现有服务栈；新建 HTTP 服务可用 FastAPI + 有界并发/超时 | 按实际 SLA、模型和数据库耗时设计；需要排队时可异步，衡量排队时间，不能承诺实时。 |
| 在线或近实时持续事件处理 | 简单场景使用现有消息消费 + 可观测 Worker；状态、窗口、多源事件复杂时评估 Flink 或 Spark Structured Streaming | 先确认事件源、吞吐、延迟、乱序、状态和恢复需求；微批可用于近实时；不因有消息队列就自动上流处理集群。 |
| 将离线、在线或流式加工接入平台，作为算子服务 | 平台适配层 + 独立处理管线；执行层按前述场景选择 | 平台 HTTP 可能是数据面，也可能仅提交任务/启动作业；先确认调度、状态、重试和实际数据通道，避免重复调度。 |

异步表示提交后可先返回；分布式表示多节点协作；并发表示多个工作在重叠推进。三者并不等价。Celery 也可多机分布式；Ray/Spark 可单机运行。不要因为数据被描述为“大规模”就自动上集群：先判断瓶颈是否为 API 配额、存储带宽、CPU、GPU、内存或网络。外部模型 API 的全局限流不会因增加 Worker 消失。

## 二、共同工程原则

1. 实现最短可运行主路径：入口 → 参数校验 → 业务服务 → 外部适配器 → 结果；模块边界只按真实职责划分，避免为少量逻辑设计多层工厂/注册器/抽象基类。
2. 使用现有的成熟库和团队依赖，不因零依赖而手写 HTTP 框架、队列、数据库连接或复杂解析器；Python 标准库适合简单任务，不一概禁止。模型优先使用已有 SDK，否则根据同步/异步选择 HTTPX 等库。
3. 主流程函数应能从入口直接追踪，清晰命名。保持提示词、工具决策、数据转换和模型调用的责任边界；避免全局隐式状态、动态导入、过度包装和隐藏控制流。
4. 配置从明确的环境变量或配置文件注入，禁止提交真实凭据、内部地址或企业数据。默认日志不记录密钥、完整敏感内容、未经许可的提示词和模型响应。
5. 显式设置网络连接/读取超时和资源上限；只对明确可恢复的失败做有限重试、退避和抖动，尊重下游速率限制。不要把参数错误、认证错误或永久失败无限重试。
6. 边界校验一次；在知道如何处理处捕获具体异常。保留异常链和上下文，避免层层 catch、裸 except、吞错、静默 fallback、返回伪成功、重复记录同一异常。可恢复的单条坏数据与整个任务失败分开统计。
7. 日志保持结构化且可读，至少包含 request_id 或 trace_id、task_id（适用时）、阶段、错误类型和耗时；加工记录版本、输入输出数量与失败数。让调用方看到稳定错误码与简洁消息，详细堆栈只进安全日志。
8. 任务/模型调用可重复，副作用未必可重复：显式考虑幂等键、结果去重、重复调用费用、幂等写入和原子提交；不宣称消息队列提供恰好一次执行。
9. 对可观测性、权限和测试按实际需要实现；不为假想风险堆砌通用框架。必要的输入校验、鉴权和明确错误处理不得省略。

## 三、场景 A：业务知识和企业数据库问答

推荐主链路：HTTP 请求 → 参数/身份校验 → 意图与业务规则 → 已授权的检索或查询工具 → 模型生成/结构化解析 → 响应。系统需要的工具才接入；简单查库不强制上向量数据库或 Agent 框架。

- 界定知识来源、数据访问范围、用户身份与权限、数据新鲜度、结果是否需要来源。无法获取真实 schema、平台权限或模型配置时，以接口契约和测试替身开发；明确标记未验证，不猜测表结构/业务事实。
- 数据库凭证使用最小权限；使用参数化查询。若让模型产生 SQL，使用只读账号、数据库侧权限与限制，并验证允许范围；绝不单靠提示词限制写操作。按需限制行数和查询时间。
- 提示词、工具输入输出和模型客户端隔离。校验模型输出格式，无法满足时返回可理解的失败或明确的业务降级；不要捏造事实。
- 外部服务为同步 SDK 时，在同步路径函数或线程池中调用；`async def` 内不要直接执行阻塞 I/O。异步并发只用于互不依赖的调用，并遵循下游限额。流式响应仅在上下游协议支持时启用。

示意目录（适合从零创建；既有项目沿用原结构）：

```text
app/
  main.py                # 应用入口、路由注册
  api/                   # 接口、请求/响应模型
  services/              # 业务流程、提示词与工具编排
  clients/               # 模型、数据库或检索访问
  config.py              # 配置
```

## 四、场景 B：离线、在线及近实时数据加工

先确定“谁拆分数据、谁运行、结果在哪里、如何恢复”。文件、对象存储或数据库存放数据；队列默认传递任务 ID、分片范围或可访问 URI，避免把大文件和敏感数据塞进消息。

- **小批量单机**：函数/CLI + 有界批次；I/O 并发、CPU 进程、GPU 批推理根据实测选择。记录总数、成功、跳过、失败及输出位置。
- **Celery + RabbitMQ**：API/生产者提交任务 → Broker 投递 → Worker 读取分片并写入持久存储 → 按需查询状态。明确 Worker 并发、重试策略、消息确认、持久化、故障恢复与幂等；基于实际部署配置，不承诺默认不丢不重。结果后端不是 Broker 的同义词；业务结果可保存在数据库或对象存储。
- **Ray Data**：多节点可访问输入；明确数据分块、CPU/GPU 资源、batch size 和 Actor 生命周期，尽量复用模型。关注 GPU 显存、读取供给、数据传输和失败处理；不要每条数据反复加载模型。
- **Spark**：优先 DataFrame/SQL 内置表达式，按需处理去重、join、聚合；理解分区和 Shuffle，避免把整个数据集 collect 到 driver。检查倾斜、小文件和存储开销。外部模型 API 与 Spark 任务重试结合时需特别处理限速和幂等。
- **在线请求加工**：典型链路为接收单条或小批数据 → 参数校验 → 复用模型或模型服务 → 加工 → 返回结果。明确端到端延迟预算、并发与背压、鉴权、超时、错误码及下游容量。短时微批聚合应计入排队延迟；请求需要较长运行时，按业务契约提供异步受理和查询/回调，不将异步自动归为离线。
- **持续流式/近实时加工**：典型链路为事件源 → 消费/变换或推理 → 结果流/存储。定义事件 ID、事件时间与处理时间、容忍乱序/迟到、重放、重复事件、积压、状态恢复及输出幂等。需要有状态窗口或跨事件关联时再评估流处理框架；复杂性与实时要求不足时使用已有消费服务。检查端到端语义；框架内的处理保证不能自动扩展到外部模型调用或其他有副作用的输出。
- **批流衔接**：历史数据全量回填可按离线管线运行，新增数据按在线或流式管线处理；明确切换水位、重叠区间去重、相同字段/规则/模型版本及结果一致性。统一共享业务转换逻辑，是否共用物理执行引擎按现有平台决定。
- **模型接口作为瓶颈**：估算输入量、每条请求及 Token 消耗、全局 QPS/TPM 和成本；控制全局并发与退避，必要时使用服务方批量接口；并发或机器数增加不等于吞吐线性增加。
- **GPU 本地推理**：确认模型能放入显存，按实测选择 batch 并处理坏样本；记录实际吞吐与资源利用，不以框架名称承诺性能。

## 五、跨场景：将离线、在线或流式加工封装为平台算子服务

先区分并核验以下两个独立契约；平台现有协议与代码优先，以下字段和状态仅为示例，不能伪装成真实平台标准。

**平台适配层**负责：按已有契约接收 HTTP/消息、鉴权与校验、映射内部请求或任务、返回约定响应、查询/回调和错误转换。**管线层**负责：读取输入、必要的分片、业务加工、写入输出、统计与记录版本。平台适配器不要直接把提示词、模型调用和文件循环全部堆在路由中。

- **离线作业型算子**：平台 POST 数据集 ID、清单或 URI 等任务描述 → 校验和可靠受理 → 选择执行器加工有界数据 → 查询/回调结果；是否异步及具体状态按平台契约确定。
- **在线请求型算子**：平台 POST 单条/小批数据 → 校验 → 调用管线 → 在 SLA 内同步返回结果，或按协议异步受理；提供 request_id，按实际协议区分成功、超时和失败。不需要后台队列时不要强加 Celery。
- **持续流式算子**：平台 HTTP 调用可能只启动、配置、停止或查询作业；实际记录可能经消息通道持续流入，输出到消息通道/存储。核实控制面与数据面的边界，定义 checkpoint、积压、背压、乱序、重放、去重和可恢复性；按真实平台实现。

以上是三种常见交付形态而非硬边界。每种均可能单机或多机、同步或异步，不默认一个平台必须支持全部模式。

与平台核对：

- 谁生成 task_id / job_id，是否提供 request_id、tenant_id、幂等键；重复 POST 的期望响应。
- 输入是 JSON 数据、数据集 ID、文件路径、对象存储 URI 还是清单；存储位置和凭据如何授予，Worker 节点是否可访问；字段映射、批次范围和数据格式。
- 同步返回还是异步；是否支持 202；查询 URL / 回调地址、鉴权、超时、回调重试、取消和超时后的处理由谁负责。
- 状态定义和终态、进度口径、部分成功的表达、平台与服务谁是状态权威；错误码和可重试/不可重试分类。
- 输出位置和格式、原始数据 ID 的对应关系、结果有效期、原子写入/失败清理，以及模型、提示词和管线版本。
- 资源与并发约束、模型/数据服务的全局限速、任务重试归属；防止平台和 Worker 同时无界重试。

示例：离线作业型算子的提交请求（仅说明字段角色，须适配平台实际协议）：

```json
{
  "task_id": "job-001",
  "input": {"uri": "s3://example-bucket/input/manifest.jsonl", "format": "jsonl"},
  "output": {"uri": "s3://example-bucket/output/job-001/", "format": "jsonl"},
  "parameters": {"batch_size": 32, "pipeline_version": "v1"}
}
```

示例异步响应：HTTP 202，`{"task_id":"job-001","status":"accepted"}`；若平台要求其他响应，则遵循其要求。接受任务不等于完成；仅在任务已可靠持久化/移交后返回 accepted。应处理数据库写入与消息发布之间的失败窗口（如使用事务性 outbox 或平台已有机制），不要在保存状态失败、消息丢失时伪称成功。大文件不要在请求体内默认传输。

在线请求型示例：`POST /operators/classify` 携带 `{"request_id":"req-001","data":{"text":"设备振动异常"}}`，同步响应可返回 `{"request_id":"req-001","result":{"category":"设备异常"}}`。路径、字段和业务值均为示意，不是已知平台协议；若实际接口使用异步或其他字段，以实际契约为准。

任务状态示例（仅适用于协议中有持久任务的情况）：`accepted → running → succeeded | partially_succeeded | failed`；取消、重试和终态规则按真实协议定义。接口至少能表达任务 ID、状态、处理总数/成功数/失败数、结果位置、可读错误和更新时间。结果与状态以可靠存储为准，不以进程内字典充当生产持久化。

## 六、实施及交付检查

1. 阅读现有代码和平台契约；写明在线/离线时效、批/流数据形态、是否平台算子、同步/异步、数据流、处理规模、资源、瓶颈假设及选型。明确服务入口、任务入口、处理函数和运行方式。
2. 从一条真实主路径落地：请求 → 执行 → 可验证输出；外部依赖缺失时明确哪些环节仅通过替身验证，不伪造线上连通性。
3. 按风险选必要测试：API 输入输出、实际平台契约映射、核心加工正确性；涉及队列/多次投递时验证幂等与失败恢复；涉及限流或外部服务时测试超时及错误分类。低风险改动不为凑数量编写镜像实现的测试。
4. 给出最短启动命令、必要配置名称、一个输入/输出示例、主入口位置、实际运行/测试结果和未验证项。没有证据时不宣称多机、GPU、压测、生产可靠性或平台对接已完成。
5. 自查：能否在两三步找到入口和失败位置？异常是否保留根因而不是吞掉？是否引入无用途组件或层层封装？是否能说明每个基础设施存在的理由？
